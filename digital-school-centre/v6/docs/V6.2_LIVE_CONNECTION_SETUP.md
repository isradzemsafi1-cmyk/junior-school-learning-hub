# V6.2 — Supabase authentication and live academic-core connection

## What this milestone adds
- Supabase Auth sign-up, sign-in, sign-out and password-reset request.
- Secure first-school onboarding through `create_school_workspace()`; the authenticated caller becomes the first owner.
- School workspace resolution from the authenticated user's membership.
- Live Supabase CRUD for academic years, grades, streams, staff, learners and learning areas.
- Tenant ID is always taken from the selected authenticated school workspace.
- Migration adds stricter role-based policies and prevents browser clients from editing membership roles.

## Required project setup
1. Create a NEW Supabase project for V6 development. Do not use the V5 production database.
2. In Supabase SQL Editor, run in order:
   - `database/001_v6_foundation.sql`
   - `database/002_v61_tenant_integrity.sql`
   - `database/003_v62_auth_onboarding_rls.sql`
3. In Supabase Project Settings → API, copy the Project URL and the public anon/publishable key.
4. Copy `app/supabase-config.example.js` to `app/supabase-config.js`.
5. Edit `app/supabase-config.js` with the Project URL and public anon/publishable key.
6. Never use a `service_role` or secret key in browser JavaScript.
7. Serve the `app` directory over localhost or HTTPS and open `live.html`. Do not rely on opening the file with `file://` if browser module/CDN restrictions apply.
8. In Supabase Auth settings, configure the site URL and allowed redirect URLs for the actual preview domain.
9. Create a test user, verify email if enabled, sign in and create one fictional test school.
10. Test with a second test account and confirm it cannot see the first school's workspace.

## Current live workspace capabilities
- Auth UI: email/password sign-up, sign-in, password reset request, sign-out.
- School onboarding: one school per account in this initial flow.
- Live data: academic years, grades, streams, staff, learners and learning areas.
- Record deletion prompts before delete.
- School membership and tenant scope are enforced by RLS.

## Important limitations / security gates
- No Supabase project credentials were supplied in this work session; therefore no real project has been connected, no SQL has been applied remotely, and no live login has been tested.
- `live.html` is a connected client once configured; it is not proof of a deployed production service.
- The current policy model is an initial school-admin/academic-office model. Teacher assignment-specific access, parent-to-learner access, MFA enforcement, invitation/member management, detailed audit triggers, privacy retention workflows and security review are still required.
- Do not use real child data until policies are independently reviewed and all acceptance tests pass.
- The live interface currently exposes school setup CRUD only. It does not yet include timetables, examination marks, finance or parent portal operations.
- Do not expose the database's service-role key to the browser or commit `supabase-config.js` with credentials to a public repository.
