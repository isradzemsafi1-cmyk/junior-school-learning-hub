# V6.5 verification and release gates

## Stage 0 – safety
- [ ] Confirm the Supabase project is a new, isolated V6 development project.
- [ ] Confirm the existing Junior School Learning Hub/V5 project is not selected.
- [ ] Export a backup and record the current migration history.
- [ ] Confirm browser configuration contains only the V6 URL and public anon/publishable key.

## Stage 1 – migration integrity
- [ ] Apply migrations 001–006 in the documented order in a disposable development project.
- [ ] Confirm migration 004 creates `timetable_requirements_id_school_unique` before the timetable-entry foreign key.
- [ ] Confirm all foreign keys and RLS policies exist and no migration errors were suppressed.
- [ ] Confirm `authenticated` cannot directly UPDATE assessment lifecycle rows, report snapshots or timetable versions.

## Stage 2 – two-tenant isolation
Create School A and School B with fictional users and learners.
- [ ] School A user cannot SELECT, INSERT, UPDATE or DELETE School B rows.
- [ ] Changing a client-supplied `school_id` does not grant access.
- [ ] A teacher with a linked staff profile can read/write marks only for an assigned, qualified learning area.
- [ ] An unassigned teacher cannot read/write those marks.
- [ ] A class teacher without an explicit assignment receives no broad mark access.

## Stage 3 – assessment lifecycle
- [ ] Only `draft -> open -> submitted -> moderation -> approved -> locked` is accepted.
- [ ] Invalid transitions are rejected.
- [ ] A non-leadership user cannot approve, lock or archive.
- [ ] A mark cannot use a component from another assessment.
- [ ] A mark cannot be attached to a learner outside the assessment grade.
- [ ] Approved, locked and archived marks cannot be inserted, updated or deleted.
- [ ] Report snapshots cannot be updated or deleted by authenticated users.

## Stage 4 – timetable and reporting
- [ ] A timetable cannot be treated as published merely because a draft version exists.
- [ ] Test teacher, class/stream and room clashes using deliberately conflicting entries.
- [ ] Confirm publication fails on conflicts and empty versions.
- [ ] Confirm report snapshot insertion is append-only and duplicate generation is handled as a new workflow decision, not an UPSERT.

## Stage 5 – application and recovery
- [ ] Test sign-in, sign-out, password reset and school membership handling.
- [ ] Test all operations using fictional data on the separate Netlify preview.
- [ ] Test restore from backup into a separate disposable project.
- [ ] Review privacy, data retention, audit trails, accessibility and low-bandwidth behaviour.

**Release decision:** any unchecked item blocks production use. Passing SQL review or static checks is not equivalent to passing these live tests.
