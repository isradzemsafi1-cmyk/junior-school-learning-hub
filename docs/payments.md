# Payments and premium materials

STK initiation authenticates the existing learner session, takes prices from the server catalog, creates the existing Supabase payment row, registers the request in Netlify Database, and sends Safaricom a signed callback URL. Drafts and previews reject STK initiation. No keys belong in browser code or this document.

The callback authenticates new requests using their signed URL, retains its metadata in a durable inbox, matches the payment, phone, product and amount, and independently queries Safaricom. Verified confirmations have unique receipt and payment identifiers. The correct Supabase row is updated to `success`, with `mpesa_receipt` and result details, before access is granted. Transient errors are retried every five minutes. Duplicate confirmations keep the original expiry. Historical requests retain the original callback endpoint.

`payment-status` and `premium-materials` validate the learner session server-side. Access lasts 24 hours from first successful verification and requires both the confirmation ledger and a currently successful matching Supabase payment. Reversed/refunded payments must be marked accordingly in the existing payment record by the trusted reconciliation process; this integration does not infer reversals from STK callbacks, which do not provide a reversal feed. A reversal recorded in Supabase blocks subsequent protected requests, and callback retries cannot restore that row to success. No public endpoint accepts reversal status updates from learners.

## Add materials later

Upload files through trusted administrative tooling to the site's Netlify Blobs store named `premium-materials`. Use keys `<product_id>/<filename>`, for example product IDs `premium_quizzes`, `grade8_notes`, `grade9_notes`, or `online_tuition`. Filenames may contain letters, digits, spaces, underscores, hyphens and single dots, up to 120 characters. Nested filenames and `..` are rejected. Do not place paid files in the public site directory. No learning content was created or removed by this change.

The website lists uploaded files after verifying access and downloads each through `/.netlify/functions/premium-materials?product_id=...&file=...`. Empty products show that materials have not yet been uploaded. These are protected file downloads; an interactive premium quiz player and an administrative uploader can be added later using the same authorization check. There is intentionally no public upload endpoint.

## Configuration and validation

Keep the existing Supabase and Safaricom server credentials configured securely for function runtime. `MPESA_ENVIRONMENT` accepts `sandbox` (the existing default) or `production`; both OAuth and STK verification use the same environment. Live credentials and the matching shortcode/passkey are required before selecting production. `MPESA_TRANSACTION_TYPE` defaults to `CustomerPayBillOnline`; use the transaction type approved for the merchant account. `MPESA_CALLBACK_URL` remains the site's HTTPS `/.netlify/functions/mpesa-callback` URL; new requests derive a signed callback route on that origin. Keep production callbacks public and exempt from site-load authentication; application sessions are not required for Safaricom delivery.

Netlify applies the generated database migrations during its managed deployment lifecycle. The durable inbox and registered requests use Netlify Database; existing Supabase payments are retained and updated as requested. Existing active legacy entitlements remain eligible through a compatibility check that never rewrites Supabase records. Access requires a matching owned successful payment with result code zero, its unique receipt and checkout, the correct catalog amount, and an independent successful Safaricom STK status query. New registered requests cannot use this fallback. The entitlement and payment are checked again after verification; the original expiry is retained without rewriting or renewing either record. The first independent verification saves immutable evidence in Netlify Database, keyed to the exact payment, entitlement, owner, product, receipt and provider request identifiers. Its expiry is capped at the original entitlement expiry. Subsequent protected requests reuse that evidence while still checking the current successful payment, active entitlement, unique receipt and original identifiers; they do not query Safaricom again. This prevents repeated listing/download checks from causing provider HTTP 429 rate limits. First-time verification still fails closed if the provider is unavailable. Only read-only status queries have one bounded retry for a short provider cooldown; STK initiation is never retried. Pending, failed, expired, reversed and refunded purchases remain locked.

Run `node --test tests/*.test.mjs` for network-mocked tests. Tests never initiate an STK push. Validate hosted preview routing, unauthenticated denial, and the preview payment guard before releasing production. Use synthetic fixtures in isolated tests for successful callback processing; never replay a fixture against customer records. A protected preview returning 401 at the site gateway does not establish function-level validation. Confirm migration application in the managed preview as well. Historical pending payments with no successful callback metadata cannot have receipts reconstructed from the STK status query alone.

## Hosted preview diagnostics

`preview-payment-verification` is a preview-only verification runner. It refuses production requests and requires a deployment-bound server signature. It exercises the same callback, status, and materials handlers with simulated authentication, Supabase records, and Safaricom verification. Real Netlify Database fixture operations use one transaction that always rolls back, and a temporary marker in the separate `mpesa-preview-verification` Blobs store is deleted afterward. Synthetic tests never write customer payments or the premium materials store. The runner also reads existing active legacy purchases and independently queries their Safaricom status to verify compatibility and protected listing access; it never initiates an STK push. Legacy fixture listing/download and the real legacy learner's download authorization use a temporary non-learning marker in the strongly consistent test store. Verification evidence created during a hosted run also rolls back. The real learner's listing reads the premium store without writing it. The optional signed `suite=dependencies` diagnostic isolates read-only Supabase, provider status and premium-store access; it never certifies access and cannot replace the full managed suite. Real customer downloads require actual uploaded materials; none are invented.

A manual draft upload may lack the managed preview's Database runtime binding even when migrations are applied and the managed callback can query its registry. Such a draft cannot establish successful hosted state verification. Run the diagnostic on a managed preview containing the current code, with its database binding present. HTTP 503 with `missing_database_binding` reports this deployment configuration problem without exposing connection credentials. A passing fixture run verifies deployed handler logic and actual platform storage; it does not certify live Safaricom credentials or perform a customer payment.
